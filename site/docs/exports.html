Reports and exports

The indicator files and the YARA rules are the machine-readable output of a run. They carry only what the board checked, and each row says how it was checked.

What feeds each file#

Every export is built from the board and the sample, never from an agent's prose. A finding reaches a file only through the status it has on the board; Reports has the table of statuses and files. Unconfirmed claims, refuted findings and refused posts never appear in an indicator file or a rule.

iocs.csv#

One row per indicator, with a header line and CRLF line ends. The sample's own hashes come first, then the checked findings. Three lines of the file of the demo run, the header, the MD5 row and the URL row:

demo/sfaef16e6/out/iocs.csv
tlp,group,type,indicator,defanged,evidence,offset,findings,context,run
AMBER,Hash values,MD5,d0e6226b2c5e01d1f8bc9c46c32591be,d0e6226b2c5e01d1f8bc9c46c32591be,computed,,,Sample file. Computed by swarmlabre from the file itself.,sfaef16e6
AMBER,URLs,URL,https://updates.example.test/check,hxxps://updates[.]example[.]test/check,byte-checked,0x95,f2,"Update URL. byte-checked, offset 0x95, finding f2.",sfaef16e6
ColumnHolds
tlpthe marking of the run
groupthe kind of indicator: Hash values, IP addresses, URLs, Host artifacts and so on
typethe type inside the group, such as SHA-256, URL or Windows file path
indicatorthe real value, so that a blocklist can use it
defangedthe same value written so that it is not a live address: hxxps://updates[.]example[.]test/check
evidencebyte-checked, call-cited or computed
offsetwhere the bytes are in the file, in hex; empty for computed rows
findingsthe board's finding ids behind the row
contextthe finding's title, how it was checked and a note when it is a private or reserved address
runthe run id

A cell that starts with =, +, -, @, a tab or a carriage return gets a leading single quote, so that a spreadsheet reads it as text and not as a formula.

iocs.stix.json#

A STIX 2.1 bundle. It holds an identity, the TLP 2.0 marking definition and its extension definition, a file object for the sample with its hashes and size, one indicator for each row STIX can express, and a report object that lists them.

RowSTIX pattern
a hash of the samplefile:hashes
a public IPv4 or IPv6 addressipv4-addr:value or ipv6-addr:value
a domaindomain-name:value
a URLurl:value
an email addressemail-addr:value
a user agentan http-request-ext request header on network-traffic
a registry keywindows-registry-key:key

Paths, Android names, other strings, hex strings that came from findings and private addresses have no honest STIX pattern, so they get no indicator; they stay in the CSV and the MISP event. Every indicator has indicator_types of unknown, because SwarmLabRE does not judge whether a value is malicious. confidence is 85 for byte-checked, 50 for call-cited and 100 for computed, and the indicator carries x_swarmlabre_evidence and, when known, x_swarmlabre_offset. In the demo run the bundle has one URL indicator and the three hash indicators.

iocs.misp.json#

One MISP event with an attribute per row, the tag tlp:amber (or the run's marking), published false and distribution 0, so nothing is shared until you change that. The threat level is 4 (undefined) and the analysis state is 2 (complete).

RowAttribute typeCategory
a hash of the samplemd5, sha1, sha256 or imphashPayload delivery
an IP addressip-dst, or ip-dst|port when the finding has a portNetwork activity
a domaindomainNetwork activity
a URLurlNetwork activity
an email address or a user agentemail-src or user-agentNetwork activity
a hash-length hex string found in the filemd5, sha1, sha256 or sha512Payload delivery
a registry keyregkeyArtifacts dropped
a file path or namefilenameArtifacts dropped
anything elseotherOther
to_ids is true only for byte-checked or computed values of a kind that detection can match: the hashes of the sample, public addresses, domains, URLs, email addresses, user agents and registry keys. It is false for file paths, private addresses and for hex strings found inside the file, which may be a key or an id. In the demo run the URL and the three hashes have to_ids true; the documentation address and the two paths have it false.

detection.yar#

The file holds one to three rules written from the strings SwarmLabRE byte-checked in the sample. This is the file of the demo run:

demo/sfaef16e6/out/detection.yar
// Agent Swarms run sfaef16e6. TLP:AMBER. Prepared by swarmlabre on 2026-11-13.
// Every rule was matched against the source sample by swarmlabre's own matcher (not by YARA) before it was written here.

rule Swarmlabre_ELF_4f514261553c {
    meta:
        description = "Byte-checked strings from the Linux ELF sample, SHA-256 4f514261553c3026... (4 strings, at least 3 must be present)"
        author = "swarmlabre"
        date = "2026-11-13"
        reference = "Agent Swarms run sfaef16e6"
        hash = "4f514261553c3026e9c926b58395d14446e8fbab6799dbc6dc4dd3749bcaf564"
        tlp = "AMBER"
        sample_type = "Linux ELF"
        source = "strings swarmlabre byte-checked in the sample"
        false_positives = "see the note in the report; not tested on clean files"
    strings:
        $s1 = "https://updates.example.test/check" ascii
        $s2 = "Global\\Demo2Lock" ascii
        $s3 = "/tmp/.demo-cache" ascii
        $w1 = "C:\\Demo\\agent.dll" wide
    condition:
        uint32(0) == 0x464c457f and filesize < 1MB and 3 of them
}

A string goes into a rule only when its finding is verified and byte-checked and has the kind ioc, crypto or config. SwarmLabRE reads the bytes at the finding's offset again and drops the string if they differ. Filters then drop strings that are shorter than 8 characters (hex strings: 12 bytes), ordinary words, ordinary prose, system or library paths, documentation and licence addresses, common library strings, strings with too little variety, format strings, version numbers, and strings that overlap or repeat one already chosen. A rule has at least 4 and at most 40 strings. When fewer than 4 pass, no rule is written and the report says why.

The condition checks the file type (uint32(0) == 0x464c457f for ELF, uint16(0) == 0x5a4d for PE, uint32(0) == 0x04034b50 for APK), a size bound of twice the sample's size rounded up to whole megabytes, and N of them, where N is a third of the strings, rounded up, and at least 3. When at least 4 of the strings are network or configuration strings, or cryptography strings, and they are not all of them, they also get a rule of their own with the suffix _net or _crypto.

SwarmLabRE does not run YARA. It matches each rule against its own copy of the sample with a matcher that implements only the part of YARA these rules use, and a rule that does not match every one of its strings is left out. The copy of a rule shown in report.html writes the dots, colons and at signs of addresses as \xNN escapes, so that the report shows no live address; the file has the real strings. The rules were checked only against the sample they came from and not against clean files. Run them over your own clean set before you block on one.

Using the files#

  • Open iocs.csv in a spreadsheet. The defanged column is the one to paste into a ticket or a message.
  • Import iocs.stix.json into a threat intelligence platform that reads STIX 2.1. Each indicator keeps its evidence level in x_swarmlabre_evidence.
  • Import iocs.misp.json as an event. It arrives unpublished and for your organisation only.
  • Give detection.yar to a scanner that reads YARA after you have tested it on files you know are clean.
  • Rebuild all of them from a stored run with python3 -m swarmlabre report RUN --out DIR. The files carry the run's TLP marking: --tlp on run or [swarm] tlp sets it.
