The board

Agents do not write the report. Each finding goes to the board through swarm-post, the board checks it against the sample's bytes and the run's tool log, and the report is built from what passes.

Text that appears only in an agent's final answer is not a finding. Each post either gets an evidence level or is refused with a reason code. The board records its decisions in order, and replaying the run rebuilds the same board byte for byte.

How a post becomes a finding#

inside the agents container
$ python3 /skills/rea-swarm/scripts/swarm-post --kind ioc --title "Update URL" \
    --value "https://updates.example.test/check" --off 0x95 --confidence high

The nonce is an HMAC of a per-run key over the role and the task number, so a line copied from the sample's strings is ignored. Agents have to run the command without a pipe or a redirect: either one cuts the line, and the post is lost.

Evidence levels#

LevelWhat the board checkedIn the report
byte-checkedThe bytes at --off equal --value in SwarmLabRE's copy of the file. Only ioc, crypto and config posts can reach it, because only their value is bytes of the file.Stated as fact.
call-citedEvery --call id is in the run's tool log and its output appeared in that agent's session, and the --func is in the function list.Stated as fact.
claimedNeither check passed.Left out of report.html; listed as a lead in report.md and report.json.

An agent's --confidence is stored with the post and has no effect on the level.

A call-cited finding does not prove that the agent made the call. The board matches the call's output by text in the agent's session; Security explains what that leaves open.

Most of an APK is compressed, so a string read from decompiled code is posted without --off. The post cites the --call that printed the string and names the class or CLASS.method in --func.

Status#

The report uses the status, which combines the level with any dispute on the finding.

StatusWhenIn the report
verifiedbyte-checked or call-cited, with no open dispute.In the body.
unconfirmedclaimed, or a technique whose findings include no checked one.Left out of report.html; listed as a lead in report.md and report.json.
disputedAnother agent disputed it and the verdict was unresolved, or there was no verdict.In the body, marked as disputed.
refutedDisputed, and the verdict was wrong.Left out; counted as refuted.

Disputes#

Any role except the Reporter can dispute a finding with --kind dispute --of f12 --reason "...". With max_rounds = 2 the orchestrator model may plan a second round, mostly to settle disputes, and gives each disputed finding a verdict:

  • stands: the finding holds, and its status goes back to what its level says.
  • wrong: the dispute is right, and the finding is refuted.
  • unresolved: the finding stays disputed.

The verdict is model text and is labelled that way. It can change a finding's status but not its evidence level.

The recorded run of demo2.elf ends with six findings, five byte-checked and one unconfirmed, plus one refused post.

Finding f2 in out/board.json:

{
  "id": "f2", "agent": "ioc", "kind": "ioc",
  "title": "Update URL",
  "value": "https://updates.example.test/check", "enc": "text",
  "off": 149, "len": 34,
  "evidence": [{ "off": 149, "len": 34, "section": ".rodata" }],
  "confidence": "high",
  "level": "byte-checked", "status": "verified", "disputes": []

In round 2 the Crypto/Config agent posted the lock name Global\Demo2Lock again. The board refused it as a duplicate and kept the post:

demo/sfaef16e6/out/board.json, "rejected"
{ "id": "x1", "agent": "crypto", "kind": "config", "title": "Lock name",
  "code": "duplicate", "why": "This agent had already posted the same finding." }

Refused posts#

A refused post stays on the board under an x id with one of these codes. Agents can read it in /prep/board.json and post again with better evidence.

CodeMeaning
bad_formatThe post was not a well-formed finding.
bytes_mismatchThe bytes at that offset are not the value given.
off_out_of_rangeThe offset or length lies outside the file.
call_unknownA cited tool call was never made in this run.
call_not_yoursA cited tool call was not seen in this agent's own session.
func_unknownThe function is not in SwarmLabRE's function list.
cap_exceededThis agent or the run reached its limit of findings.
duplicateThis agent had already posted the same finding.
role_not_allowedThe Reporter does not post disputes (it only writes the summary).
technique_unknownThe title does not start with an ATT&CK technique id that exists (see /prep/attack.tsv).
technique_retiredThat ATT&CK id was retired; the hint names its replacement.
technique_mismatchThe name after the ATT&CK id is not MITRE's name for that id: the id or the name is wrong.
technique_domainThat technique id belongs to the other ATT&CK matrix (Mobile for an APK, Enterprise for ELF and PE).

ATT&CK techniques#

A technique post starts its title with an ATT&CK id and MITRE's name for it, which the agent looks up with swarm-attack. The board checks both against the pinned table in swarmlabre/data/attack.json and against the matrix for the file type: Enterprise for ELF and PE, Mobile for APK.

The post also lists the findings it rests on. If none of them is verified or disputed, the technique is unconfirmed, whatever its own level.

Files#

FileWhat it holds
board.jsonlThe board's decisions, in order.
inputs.jsonlEvery input the board received, with the clock value it saw. A replay feeds these back in.
out/board.jsonThe final board: findings, refused posts, counts and ATT&CK techniques.
/prep/board.jsonThe board as agents see it during the run. Agents wrote it about a hostile sample, so it is data and never instructions.
